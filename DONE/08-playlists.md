# ТЗ-08: Видео-плейлисты через сюжеты (story с типом video → плейлист)

Статус: финальная версия v2, к реализации.
Дата: 2026-11-08.
Связи: существующие `stories` + `article_stories` (`packages/db/src/schema.ts`),
`GET /stories/:slug` (`apps/api/src/routes/stories.ts`), `StoryPage.tsx`,
`toEmbedUrl()`/`videoThumbnail()` (`apps/web/src/lib/video.ts`), админ-конструктор
`StoryEditPage.tsx`. Миграции — drizzle-kit, последняя на сегодня `0013_video_type.sql`.

> Вводная владельца: «плейлисты. у нас сюжеты?» — являются ли сюжеты нашими
> плейлистами или нужны отдельные видео-плейлисты (как tagDiv video playlist)?

## 1. Цель

Дать медиа «инвестиционно.рф» возможность вести рубрики-«выпуски» видео
(YouTube/RuTube/VK) в формате плейлиста с плеером и списком серий — **без новых
таблиц и без новой сущности**, расширив существующие сюжеты (stories).

## 2. Сравнение концепций

| | tagDiv video playlist | Наши сюжеты (сейчас) |
|---|---|---|
| Суть | Плейлист видео: один главный плеер + список серий | Хронология материалов по теме (любого типа) |
| Тип контента | Только видео | Любой: novost, sobytie, analitika, interesnoe, ideya, video |
| Рендер | Плеер (embed) + сайдбар серий | Вертикальный таймлайн со ссылками на материалы |
| Навигация | Клик по серии меняет плеер без перезагрузки; autoplay next | Переход на отдельную страницу материала |
| Данные | Отдельная сущность/плагин | `stories` + `article_stories` (`is_primary`, `added_via`) |

Вывод: концепции пересекаются частично. Сюжет — уже готовый «плейлист-контейнер»
(состав, главный элемент, публичная страница, админ-конструктор). Не хватает
только **режима отображения** для сюжетов, состоящих из видео.

## 3. Рекомендация

**Видео-режим сюжета**: сюжет, в котором все опубликованные материалы имеют
`type = 'video'`, рендерится на `/syuzhet/:slug` как плейлист (главный плеер +
список серий + автопереход). Никаких новых таблиц, флагов и типов — режим
вычисляется из состава сюжета.

Альтернатива («универсальные плейлисты» из любого контента) отклонена:
плейлист из текста не имеет смысла для пользователя, а усложняет UI.

## 4. Требования

### R1. Обнаружение плейлист-режима

- `StoryPage` (`apps/web/src/pages/StoryPage.tsx`) после загрузки данных
  вычисляет: `isPlaylist = articles.length > 0 && articles.every(a => a.type === 'video')`.
- Правило строгое: **все** элементы — видео. Один текстовый материал возвращает
  сюжет к обычной хронологии (см. «Риски»).
- Пустой сюжет (0 материалов) — обычный режим (пустая хронология).
- **Решение ТЗ:** тип `type` уже приходит в `GET /stories/:slug` (поле есть в
  селекте роута и в `ArticleListItem`), отдельный флаг «это плейлист» в БД не
  вводим — режим деривативен.

### R2. Плейлист-режим на StoryPage

При `isPlaylist = true` вместо таймлайна рендерится:

1. **Главный плеер** — `<iframe>` текущей серии через существующий
   `toEmbedUrl()` (`apps/web/src/lib/video.ts`), тот же разметочный паттерн, что
   в `ArticlePage.tsx` (aspect-video, rounded-xl, allow/allowFullScreen).
   Источник видео — `articles[currentIndex].videoUrl`.
2. **Заголовок и описание** текущей серии под плеером (title + excerpt),
   ссылка «Открыть материал →» на `/{type}/{slug}` страницы материала.
3. **Список серий** — сбоку на десктопе (грид 2/3 + 1/3), снизу на мобильном.
   Каждая серия: номер, превью (`videoThumbnail()`), title, дата, бейдж
   «сейчас играет», галочка «просмотрено» (если включён прогресс, см. R4).
4. **Клик по серии** меняет `currentIndex` → плеер пересоздаётся с новым
   `src` **без перезагрузки страницы** (`key={article.id}` на iframe).

### R3. Автопереход (autoplay next)

- Тумблер «Следующее видео автоматически» (как в YouTube-плейлистах),
  по умолчанию **включён**, состояние в `localStorage`
  (`invrf:playlist-autoplay`).
- Реализация: по событию `ended` — для YouTube через postMessage API
  (YouTube IFrame API, `onStateChange` → `ENDED`); для RuTube/VK — iframe
  не отдаёт события → **принято (решение ТЗ)**: autoplay работает только для
  YouTube, для остальных платформ тумблер скрыт/выключен (заглушка на будущее).
- При включённом autoplay по окончании серии: автоматический переход к
  следующей (без цикла: последняя серия — стоп).
- **Решение ТЗ:** YouTube IFrame API грузится лениво — только в плейлист-режиме,
  один `<script src="https://www.youtube.com/iframe_api">`, инициализация плеера
  через `new YT.Player()` с `enablejsapi=1` в src iframe; на unmount —
  `player.destroy()` и удаление слушателя `onYouTubeIframeAPIReady`.

### R4. Прогресс просмотренных серий

- **Отложить (решение ТЗ).** Отдельной задачей позже (метки «просмотрено» в
  localStorage, либо серверные `article_views`, которые уже есть в схеме).
- В рамках этого ТЗ — не делаем. Бейдж «просмотрено» из R2 в MVP не рендерим.

### R5. Главная статья (is_primary) = первая серия

- Первая серия плейлиста — элемент с `isPrimary = true`, если он есть; иначе —
  первый по порядку (индекс 0 после сортировки R6).
- Плеер при загрузке страницы показывает первую серию: `currentIndex`
  инициализируется индексом `isPrimary`-элемента, а не нулём.
- **Решение ТЗ:** не плейлист сортируется вокруг `is_primary`, а стартовый
  индекс вычисляется из уже отсортированного массива — порядок серий (R6)
  и «главная» (R5) независимы.

### R6. Порядок серий (sort_order)

Текущее состояние: порядок в `GET /stories/:slug` и в `GET/PUT /stories/:id/articles`
— `ORDER BY articles.published_at ASC`; колонки `sort_order` в `article_stories`
нет (проверено по `packages/db/src/schema.ts`, строки 254–267).

- **Решение ТЗ: добавляем `sort_order` (принято расширение, MVP без него не делаем).**
  Причина: иначе API сортировки придётся менять дважды (сейчас — `published_at`,
  потом — `sort_order`), а редактор не сможет переупорядочить «выпуски» после
  публикации.
- Миграция: отдельная малая миграция **после 0014**, именуем
  `0015_sort_order_article_stories.sql` (фактический номер назначит drizzle-kit —
  если ТЗ-03/ТЗ-04 займут 0014, а другое из них 0015, миграция получит следующий
  свободный; конфликт номеров разрешается при генерации, порядок применения
  любой, т.к. DDL независимы).
- Схема: `sortOrder: integer('sort_order').notNull().default(0)` в `articleStories`.
- Сортировка везде (публичный `GET /stories/:slug`, админские
  `GET/PUT /stories/:id/articles`): `ORDER BY article_stories.sort_order ASC,
  articles.published_at ASC` (fallback на дату внутри равных sort_order).
- `PUT /stories/:id/articles`: индекс массива `articleIds` писать в `sort_order`
  (`articleIds.map((articleId, i) => ({ articleId, storyId, sortOrder: i, ... }))`).
- Backfill не нужен: `DEFAULT 0` + fallback на `published_at` сохраняют текущий
  порядок для существующих строк.

### R7. API

- `GET /stories/:slug` (`apps/api/src/routes/stories.ts`): добавить в селект
  `videoUrl: articles.videoUrl` — без него плеер на StoryPage не построить.
  В тип `StoryDetail` (`apps/web/src/api.ts`, строки 70–73) добавить
  `videoUrl: string | null` в элементы `articles`.
- Сортировка: `asc(articleStories.sortOrder), asc(articles.publishedAt)` (R6).
- `GET/PUT /stories/:id/articles` — меняются только в части сортировки/записи
  `sort_order` (R6). Сигнатура тела PUT не меняется: упорядоченный массив
  `articleIds` уже несёт порядок.

### R8. Админка

- Ничего нового не строим. Конструктор сюжетов (`apps/admin/src/pages/StoryEditPage.tsx`)
  уже умеет: состав через чекбоксы, «сделать главной».
- В `StoryEditPage` добавить переупорядочивание выбранных материалов:
  блок «Порядок серий» над списком чекбоксов — строки выбранных материалов
  (в текущем порядке `selected`) с кнопками ↑/↓, меняющими порядок в `selected`.
  **Решение ТЗ:** ↑/↓, а не drag-and-drop — дешевле, надёжнее, без новых
  зависимостей. Drag-and-drop — отложенное улучшение.
- После загрузки состава (`/stories/:id/articles`, который теперь отсортирован по
  `sort_order`) `setSelected(sa.articles.map(a => a.articleId))` автоматически
  получает правильный порядок — отдельной загрузки порядка не нужно.
- Подсказка в StoryEditPage: «Все материалы сюжета — видео → страница станет
  плейлистом» (см. Риски).

## 6. Критерии приёмки

- [ ] Сюжет, состоящий только из опубликованных `type=video`, открывается на
      `/syuzhet/:slug` в плейлист-режиме: главный плеер + список серий.
- [ ] Первая серия = материал с `is_primary` (или первый по порядку); его видео
      в плеере при загрузке.
- [ ] Клик по серии меняет видео в плеере без перезагрузки страницы.
- [ ] Тумблер autoplay включён по умолчанию; для YouTube-серий по окончании
      автоматически грузится следующая; тумблер сохраняется в localStorage;
      для RuTube/VK тумблер скрыт.
- [ ] Смешанный сюжет (видео + текст) и текстовый сюжет рендерятся прежней
      хронологией — без изменений.
- [ ] Обычные (не видео) сюжеты: регрессий нет — верстка, избранное, хронология.
- [ ] Порядок серий в плейлисте соответствует порядку, заданному в админке
      (↑/↓), а не датам публикации; у существующих сюжетов порядок не изменился
      (fallback на `published_at` при `sort_order = 0`).
- [ ] Миграция накатывается на чистую БД и на продуктовую копию без правок руками.

## 7. Тестирование

Ручная проверка (e2e-раннера в репо нет — как зафиксировано в ТЗ-04):

1. **Плейлист-режим:** создать сюжет из 3+ опубликованных видео (YouTube) →
   `/syuzhet/:slug` показывает плеер (первая серия = `is_primary`) и список
   серий; клик по 2-й серии меняет видео без перезагрузки (network: нет
   повторного document-запроса).
2. **Autoplay:** включить тумблер → досмотреть серию (или эмулировать `ENDED`
   через `player.seekTo(player.getDuration())`) → автопереход к следующей;
   после последней серии — стоп. Перезагрузить страницу — тумблер в том же
   состоянии (localStorage `invrf:playlist-autoplay`).
3. **RuTube/VK-серия:** тумблер autoplay скрыт; плеер рендерится, переход по
   клику работает.
4. **Смешанный сюжет:** добавить текстовый материал → страница рендерит
   обычную хронологию; убрать его обратно → снова плейлист.
5. **Серия без video_url / нераспознанная платформа:** превью-заглушка, клик
   ведёт на страницу материала; из автоплея исключается (после такой серии
   autoplay останавливается или перепрыгивает — по реализации, зафиксировать
   в коде комментарием).
6. **Порядок (sort_order):** в админке переупорядочить серии ↑/↓ → сохранить →
   публичный порядок изменился; даты публикации не изменились. Новый сюжет без
   ↑/↓ → порядок по `published_at ASC` (все `sort_order = 0`).
7. **Регрессия:** текстовый сюжет и смешанный — верстка и избранное без
   изменений; `GET /stories/:id/articles` (admin) отдаёт `sort_order`.
8. **Миграция:** `drizzle-kit generate` → `0015_*` применяется на dev-БД и на
   копии продуктовой; `SELECT sort_order FROM article_stories` — все 0.
