# ТЗ-07. Trending Now — тиккер «Сейчас читают» в шапке (v2 — финальная)

**Вводная владельца:** «настоящий трендинг NOW тиккер. реалтайм можно. с накоплением за 6 часов. если обновления не было — рефреш раз в 15 минут».

**Статус:** ТЗ финальное (v2), к реализации · **Приоритет:** после пейволла и метрик (использует `article_views`, публичный доступ к статьям)

---

## 1. Цель

Горизонтальная бегущая лента в шапке сайта «Сейчас читают: …», показывающая топ-N статей по реальным просмотрам за последние 6 часов. Заголовки кликабельны, ведут на статью. Даёт эффект «живого» медиа и повышает глубину просмотра, не требуя ручной модерации — рейтинг считается автоматически из `article_views`.

## 2. Текущее состояние (что уже есть в коде)

- **Данные:** таблица `article_views` (`packages/db/src/schema.ts`, строка 430) — `article_id`, `viewed_at` (timestamptz, дефолт `now()`), опциональный `user_id`; есть индекс `(article_id, viewed_at)`. Просмотр пишется при открытии статьи (`apps/api/src/routes/articles.ts`, строка 158, fire-and-forget `.catch(() => {})`) — **и только после пейволл-проверки** (строки 126–134): просмотр фиксируется только у тех, кому статья реально доступна. Следствие: счётчики в тиккере = просмотры реальных читателей, а не ботов/отказов.
- **Шапка:** `apps/web/src/components/Layout.tsx` — единый `<header>` на всех страницах (строки 20–44), тёмная тема, акцент `#beff00`. Тиккер встраивается сразу после `</header>` (между строками 44 и 45).
- **Статьи:** таблица `articles` имеет `status` (`draft | pending | published`), `accessLevel` (`public | auth | tariff`), уникальный индекс `(type, slug)`. URL статьи: `/{type}/{slug}` (по аналогии с `TrendPage`, `CompanyPage`).
- **Фронтенд:** React Query подключён (`apps/web/src/main.tsx`, `QueryClientProvider`). Хелпер `api` живёт в **`apps/web/src/api.ts`** (объект `api`, строка 75; функция `get` сверху) — не в `lib/api.ts`. Отдельного поля `viewsCount` в схеме нет — ТЗ-03 (виртуальный счётчик) ещё не реализован.
- **API:** роутеры в `apps/api/src/routes/*.ts`, регистрация в `apps/api/src/index.ts` (импорты строки 8–21, `app.use` строки 56–69). Публичных эндпоинтов без guard'ов много — прецедент есть, но см. комментарий баг 2026-11-08 в `metrics.ts` (строки 14–15): guard'ы ставить на уровне конкретных роутов, не `router.use`. Для trending guard не нужен вообще (публичный эндпоинт).

## 3. Требования

### 3.1. Поведение
1. Тиккер — горизонтальная бегущая строка (marquee) в шапке, сразу под `<header>`, формат: **«Сейчас читают:»** + циклично повторяющаяся лента `Заголовок • Заголовок • …`.
2. Клик по заголовку → переход на страницу статьи.
3. Виден **на всех страницах** (встроен в `Layout`), в компактной однострочной высоте (~32–36 px), не перекрывает контент.
4. Пауза анимации при наведении курсора (иначе клик по движущемуся заголовку недостижим). На touch-устройствах autoplay отключён полностью, лента — ручной горизонтальный скролл (**решение ТЗ**, см. риск «мобильный тач»).
5. Если за окно накопления (6 ч) нет ни одного просмотра — тиккер **скрыт целиком** (принцип 4.3: показываем только внесённое). Fallback «последние опубликованные» не используем — это подменяет реальный сигнал «сейчас читают» искусственным.
6. Пейволл: в тиккер попадают **только `status='published'` и `accessLevel='public'`** статьи. Обоснование: тиккер виден анонимам, тизерить paywall-контент (клик → модалка оплаты) в «сейчас читают» — плохой опыт и обесценивает доверие к ленте.

### 3.2. Данные
- Рейтинг: `count(*) по article_views` за окно `viewed_at >= now() - interval '6 hours'`, join к `articles` с фильтрами выше.
- N = **10** — **решение ТЗ** (не 5: при низком трафике топ-5 может «выгорать» за часы, топ-10 держит ленту живой; компактность достигается кеглем, а не числом позиций).
- При коротком списке (1–2 статьи) лента дублирует элементы, чтобы marquee заполнил строку; при 0 — скрыт.
- Формат показа: **заголовок + счётчик 👁 N** (N — просмотры за 6-часовое окно). Счётчик показываем **всегда, без порогов скрытия — решение ТЗ** (порог «скрыть если <5» добавляет недетерминированности в верстку и выглядит хуже, чем честные маленькие числа; при росте трафика числа станут больше сами). Это не «всего просмотров» и не будущий `viewsCount` из ТЗ-03; совместимость сохраняется: ТЗ-03 может позже показать тот же числовой формат, но за всё время. В ТЗ-07 используем только реальный счёт за окно — виртуальные инкременты в трендинге недопустимы (ломает честность ранжирования).

### 3.3. API
- `GET /api/trending?hours=6&limit=10` — публичный, без авторизации.
  - `hours`: 1–24, дефолт 6; `limit`: 1–20, дефолт 10. Валидация с клампом, как `days()` в `metrics.ts` (строки 18–21).
  - Ответ: `{ items: [{ type, slug, title, views }], windowHours, computedAt }`.
- **Кэш — решение ТЗ (финально, не открытый вопрос): in-memory `Map` в процессе API, TTL 5 минут, плюс досрочная инвалидация по `max(viewed_at)`.** Логика: при каждом хите выполняется дешёвый `select max(viewed_at) from article_views` (по индексу, ~мс). Если max вырос с момента `computedAt` кэш-записи — считаем топ заново, иначе отдаём кэш, пока не истёк TTL 5 мин. Это ровно компромисс из вводной владельца: «реалтайм можно» при активном трафике (новый просмотр → ближайший хит пересчитает топ), «рефRESH раз в 15 минут» в простое фактически улучшен до ≤5 мин. Если владелец захочет жёсткие 15 минут — меняется одна константа `TRENDING_TTL_MIN = 15` и убирается проверка max(viewed_at); интерфейс и все остальные пункты ТЗ не меняются.
  - Ключ кэша — `hours:limit`; значение — `{ data, computedAt, lastMaxViewedAt }`.
  - Если `article_views` пуста (max = null) — инвалидация по max отключена, работает только TTL.
- Один SQL-запрос, индекс `(article_id, viewed_at)` покрывает окно через join; при росте объёма (>1M просмотров/сутки) — пересмотреть на materialized view (отдельное ТЗ, не блокер).

### 3.4. Фронтенд
- Компонент `TrendingTicker` (`apps/web/src/components/TrendingTicker.tsx`), монтируется в `Layout.tsx` сразу после `</header>` (между строками 44 и 45).
- Данные: `useQuery({ queryKey: ['trending'], queryFn: () => api.trending(), refetchInterval: 5 * 60 * 1000, staleTime: 5 * 60 * 1000 })` — фронт не должен долбить API чаще бэкенд-кэша; при открытии новых вкладок каждая обновится по своему таймеру — приемлемо, бэкенд-кэш всё равно держит нагрузку. **Решение ТЗ:** `refetchInterval` оставляем (не mount-only) — тиккер «живой», вкладка, открытая час, покажет актуальный топ.
- Пустой `items` → компонент возвращает `null` (тиккер не рендерится, разметка не скачет).
- Marquee: CSS animation (`@keyframes translateX`, длительность привязана к ширине ленты, бесшовный цикл через дублирование контента ×2). Анимация на `transform` (GPU), не на `left`. **Обязательно:** `@media (prefers-reduced-motion: reduce)` — анимация отключена, лента заменяется на статичный горизонтальный скролл.
- Мобильная адаптация (**решение ТЗ**): на `<640px` кегль уменьшается (text-xs); на touch-устройствах (по `matchMedia('(hover: none)')` или pointer: coarse) autoplay выключен — горизонтальный скролл с snap. Критерий: заголовок читаем и кликабелен на тач-устройстве.
- Стили в духе шапки: тёмная плашка `#111` с бордюром `#2a2a2a`, префикс «Сейчас читают» — акцентный `#beff00`, счётчик 👁 — `text-zinc-500`.
- Разметка ленты — семантический список ссылок `<nav aria-label="Сейчас читают"><ul><li><Link>…</ul></nav>`, не canvas/div-портянка (screen readers, SEO-внутренние ссылки).

## 4. Реализация (чек-лист по файлам)

1. **`apps/api/src/routes/trending.ts`** — новый роутер:
   - Константы: `TRENDING_TTL_MIN = 5`, `DEFAULT_HOURS = 6`, `DEFAULT_LIMIT = 10`.
   - Кламп-парсеры `hours()` / `limit()` по образцу `days()` в `metrics.ts` (строки 18–21), но диапазоны 1–24 и 1–20.
   - Кэш: модульный `Map<string, { data, computedAt, lastMaxViewedAt }>`; функция `getMaxViewedAt()` — `select max(viewed_at) from article_views`; логика: кэш валиден, если `Date.now() - computedAt < TTL` **и** `maxViewedAt <= lastMaxViewedAt`.
   - SQL через `db.execute(sql`…`)` (стиль как в `metrics.ts`):
     ```sql
     select a.type, a.slug, a.title,
            count(*)::int as views
     from article_views av
     join articles a on a.id = av.article_id
     where av.viewed_at >= now() - make_interval(hours => ${hours})
       and a.status = 'published'
       and a.access_level = 'public'
     group by a.id, a.type, a.slug, a.title
     order by views desc, a.published_at desc
     limit ${limit}
     ```
   - Ответ: `{ items: rows.map(...), windowHours: hours, computedAt: new Date().toISOString() }`.
   - `export const trendingRouter = Router();` + `trendingRouter.get('/', handler)`. Guard'ы не вешать вообще.
2. **`apps/api/src/index.ts`** — импорт рядом со строкой 21 (`metricsRouter`), регистрация `app.use('/api/trending', trendingRouter);` после строки 61 (`metricsRouter`), до `cabinetRouter` (строка 69, у него router-wide auth — наш роутер без guard'ов должен быть до него, хотя пути не пересекаются, порядок для чистоты).
3. **`apps/web/src/api.ts`** — добавить в объект `api` (после `byType`, строки 91–92):
   - интерфейс `TrendingItem { type: string; slug: string; title: string; views: number }`;
   - метод `trending: () => get<{ items: TrendingItem[]; windowHours: number; computedAt: string }>('/trending')`.
4. **`apps/web/src/components/TrendingTicker.tsx`** — новый компонент:
   - `useQuery` как в 3.4; при `items.length === 0` → `null`.
   - Контент ленты дублируется ×2 в DOM для бесшовного цикла; hover → `animation-play-state: paused` (CSS, без JS-состояния).
   - `prefers-reduced-motion` и `(hover: none)` → статичный/ручной скролл.
   - Ссылка: `<Link to={`/${type}/${slug}`}>`.
5. **`apps/web/src/components/Layout.tsx`** — импорт `TrendingTicker`, вставить `<TrendingTicker />` между строками 44 (`</header>`) и 45 (`<main>`).
6. **CSS** — marquee-стили в `apps/web/src/index.css` (или где живут глобальные стили; Tailwind-классы для цветов, `@keyframes` и reduced-motion-оверрайд — в CSS). Длительность анимации: вычислять из ширины ленты в JS (`ref` + `scrollWidth`) или фиксированная ≥40 с — допустимо оба варианта, критерий: скорость чтения комфортна, цикл бесшовный.

## 5. Критерии приёмки

1. Тиккер виден на любой странице сайта, включая главную и страницу статьи.
2. Клик по заголовку в тиккере открывает соответствующую статью.
3. Показаны только `published` + `public` статьи; paywall-контент в тиккере отсутствует (проверка: у статьи с `access_level='auth'`, набравшей больше всего просмотров, в тиккере нет).
4. Счётчики 👁 соответствуют реальным просмотрам за 6 часов (проверка SQL-запросом руками).
5. Пустой результат (нет просмотров за окно) → тиккер полностью отсутствует в DOM, нет пустой плашки.
6. При `prefers-reduced-motion` анимации нет, лента доступна через скролл.
7. Кэш: повторный запрос `GET /api/trending` в пределах TTL без новых просмотров возвращает `computedAt` прежнего вычисления (нет повторного тяжёлого SQL — видно по логам/таймингам); после вставки нового просмотра (`insert into article_views …`) ближайший запрос пересчитывает топ (`computedAt` обновился).
8. `refetchInterval`/`staleTime` на фронте = 5 мин — запросы не чаще бэкенд-TTL.
9. При наведении курсора анимация останавливается; клик по остановленному заголовку срабатывает.

## 6. Тестирование

1. **API, кламп параметров:** `curl 'localhost:3001/api/trending?hours=30&limit=99'` → ответ с `windowHours: 24`, в `items` не более 20 строк; `?hours=0` → `windowHours: 1`; без параметров → `windowHours: 6`, до 10 строк.
2. **SQL-сверка:** выполнить запрос топа из п.4 реализации руками в psql и сравнить с ответом эндпоинта — совпадение порядка и счётчиков.
3. **Кэш-hit:** два `curl` подряд → одинаковый `computedAt`; тяжёлый SQL в логах Postgres один раз (включить `log_min_duration_statement = 0` на время теста).
4. **Кэш-инвалидация по активности:** `insert into article_views (article_id) values (<id публичной статьи>);` → следующий `curl` возвращает обновлённый `computedAt` и, если просмотров хватило, статья в топе с учётом нового просмотра. Затем удалить тестовую строку.
5. **Кэш-TTL в простое:** не вставляя просмотров, ждать 5 минут → `computedAt` обновился (пересчёт по TTL, max(viewed_at) не вырос).
6. **Пейволл:** создать/взять `auth`/`tariff` статью, дать ей больше всего просмотров за окно (тестовыми вставками) → в ответе `/api/trending` её нет; `draft`/`pending` статья с просмотрами — тоже нет.
7. **Пустое окно:** запрос с `?hours=1` в час без трафика (или на тестовой БД после `truncate article_views`) → `{ items: [] }`; на фронте в DOM тиккера нет (проверить devtools, нет пустой плашки).
8. **Фронтенд, marquee:** анимация бежит бесшовно (стык незаметен), hover паузит, клик по ссылке ведёт на `/{type}/{slug}`; в devtools включить emulate `prefers-reduced-motion` → анимации нет, скролл работает.
9. **Фронтенд, touch:** в devtools устройство без hover (напр. iPhone) → autoplay выключен, скролл с snap, ссылки кликабельны.
10. **Все страницы:** главная, `/feed`, `/pricing`, страница статьи, `/search` — тиккер присутствует и не ломает вёрстку (нет горизонтального скролла страницы из-за ленты).
11. **Счётчик честности:** просмотры фиксируются только после пейволл-проверки (`articles.ts:126–158`) — просмотр анонима закрытой статьи не попадает в тиккер; регрессия: не менять порядок «проверка доступа → insert article_views».

## 7. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Marquee недоступен (vestibular-расстройства, screen readers) | средняя | `prefers-reduced-motion` → статичный скролл; лента — обычный список ссылок в DOM (семантика `<nav><ul><li><Link>`), не canvas |
| Клик по движущемуся заголовку | высокая | hover-pause обязателен; скорость анимации умеренная (≥40 сек на цикл) |
| Мобильный тач: marquee мешает скроллу страницы | средняя | **решение ТЗ:** на touch-устройствах autoplay отключён, ручной горизонтальный скролл с snap |
| Дёрганье макета при первом refetch (появление/исчезновение тиккера) | средняя | **решение ТЗ:** высоту не резервировать — принцип 4.3: пусто = нет элемента; лучше микро-скачок, чем пустой блок |
| Кэш в памяти = разные данные на разных инстансах API | низкая (сейчас один инстанс) | при горизонтальном масштабировании перейти на общий кэш (Redis) — зафиксировать в TODO |
| Накрутка просмотров одним пользователем влияет на ранжирование | низкая | окно 6 ч и объём трафика невысоки; при злоупотреблениях — агрегировать по `distinct user_id` или IP (отдельное решение) |
| Долгий SQL при большом объёме `article_views` | низкая | индекс `(article_id, viewed_at)` покрывает; мониторить `pg_stat_statements` |
| TTL 5 мин × N вкладок у пользователей | низкая | бэкенд-кэш консолидирует нагрузку; `staleTime` на фронте предотвращает повторные фетчи при ремонте компонента |
