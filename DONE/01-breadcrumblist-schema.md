# ТЗ-01: JSON-LD BreadcrumbList (schema.org) на всех публичных страницах

- **Статус:** v2 — согласовано, на реализацию
- **Дата:** 2026-11-08 (v2)
- **Связи:** ТЗ-10 зависит от этого ТЗ — `BreadcrumbList` в бот-шаблоне (`apps/api/src/services/botRender.ts`) повторяет структуру §4 этого ТЗ 1:1 (см. §7 «Согласование с ТЗ-10»). URL 1:1 с донором — SEO-критично, не ломать.

---

## 1. Цель

Донор (WordPress, тема Newspaper) отдаёт в `<head>` разметку `BreadcrumbList` (JSON-LD, schema.org), по ней Google строит хлебные крошки в сниппете. При переезде на SPA (React 19, Vite) эта разметка пропала — рискуют позиции: сниппеты теряют строку крошек (CTR ↓), глубина обхода и понимание структуры сайта ботами ухудшаются. Задача: вернуть `BreadcrumbList` на каждой публичной странице в DOM с теми же URL, что у донора (1:1).

Результат для выдачи: сниппет вида `инвестиционно.рф › Новость › <заголовок>` и корректная передача иерархии «раздел → материал» поисковику.

## 3. Требования

### Must

1. На каждой публичной странице из §4.2–§4.7 в DOM (в `<head>` — предпочтительно; Google принимает и начало `<body>`) должен присутствовать ровно один блок `<script type="application/ld+json">` с объектом `{"@context":"https://schema.org","@type":"BreadcrumbList","itemListElement":[...]}`. На страницах, для которых §4 фиксирует «разметку не выводим» (главная, поиск, лента, кабинет, служебные, 404), блока быть не должно — это не нарушение must-1.
2. Каждый элемент `itemListElement`: `position` (1-based), `name`, `item` — **абсолютный URL**. Хост — из единой конфигурации (§6.4), без punycode/кириллицы-хардкода в компонентах. **Решение ТЗ:** все элементы, включая последний (текущую страницу), выводятся с `item` = canonical текущего URL — упрощает генератор, соответствует спецификации (у последнего элемента `item` опционален, не запрещён).
3. Имена элементов (`name`) совпадают с лейблами визуальных крошек из §2 (один источник данных — см. §6; исключение: полный заголовок статьи, см. §4.2).
4. Абсолютные URL в разметке совпадают 1:1 с URL донора для соответствующих материалов (слаг не транслитерировать, не менять).
5. Установить `react-helmet-async` (2.x), обернуть приложение в `HelmetProvider` (точка входа `src/main.tsx`), JSON-LD вставлять через `<Helmet><script type="application/ld+json">{...}</script></Helmet>`. **Решение ТЗ:** инжект голым `<script>` из `useEffect` не используем; fallback на useEffect допускается только при жёстком конфликте с React 19 (см. R4).
6. В JSON экранировать `</script>` в текстах (`<` → `\u003c`), чтобы заголовок материала не ломал вёрстку при вставке в script-блок.

### Should

7. Единый компонент-хелпер `JsonLdBreadcrumbs({ items }: { items: { name: string; url?: string }[] })`, строящий объект разметки, чтобы страницы не собирали JSON руками.
8. Совместить источник цепочки: расширить `Crumb` в `Breadcrumbs.tsx:3-6` опциональным `url?: string` и генерировать визуальные крошки и JSON-LD из одного массива на странице.
9. **Решение ТЗ (согласовано с ТЗ-10 §6.4):** подтянуть заодно `document.title` через тот же `Helmet` (title/description сейчас глобальные из `index.html:6-7`). Объём ограничиваем: меняем только `<title>` на статьях и архивах типов; `meta description` остаётся глобальным до отдельной задачи по вторичной SPA-мете (источник правды текстов для ботов — API-шаблон ТЗ-10, SPA-мета вторична, рассинхрон недопустим).
10. Зарегистрированная задача ТЗ-10 (SSR/бот-рендер) принята как зависимость; этот ТЗ закрывает только клиентскую часть.

### Не делаем (out of scope)

- SSR, пререндер, ответы спайдерботам — ТЗ-10.
- Разметка `Article`, `Organization`, `WebSite` (sitelinks searchbox) — отдельные ТЗ.
- Крошки для страниц с query-фильтрами (`/portfolio?…`) — обрабатываем по схеме §4.7.
- Визуальные крошки на SearchPage/FeedPage — отдельная задача по UI.

## 5. SPA-ограничение (известное, фиксируем)

Боты без JS (старые краулеры, некоторые агрегаторы) получат из `curl`/HTTP-ответа только `index.html` без разметки — JSON-LD в DOM появляется только после выполнения бандла. Googlebot рендерит JS (WRS), поэтому основной поисковик покроется; Яндекс умеет JS-рендеринг частично и с задержкой. **Это принятое ограничение ТЗ-01; полное решение — ТЗ-10 (бот-детект рендер на API)**, после которого разметку повторяет серверный шаблон 1:1 (структура — §4 этого ТЗ).

Требование к коду для переиспользования в ТЗ-10: генератор цепочки — **чистая функция без обращений к `window.location`/DOM** (принимает готовые `{name, url?}` и `siteUrl`), чтобы `botRender.ts` мог воспроизвести ту же структуру на сервере.

Отдельно: экран пейволла (403 на статье) — рендерится без крошек. Заголовок недоступен, slug-подстановка в `name` недопустима. **Решение ТЗ:** на 403-экране разметку не выводим (метаданные для ботов на пейволл-материалах отдаёт ТЗ-10 по своим правилам).

## 7. Согласование с ТЗ-10

1. **Хост:** ТЗ-10 использует `PUBLIC_SITE_URL` (API), этот ТЗ — `VITE_SITE_URL` (web). Решение ТЗ: оба задаются одним и тем же значением на деплое, fallback идентичен (§6.5). Расхождение хоста в JSON-LD SPA и бот-шаблона — дефект блокирующий приёмку обоих ТЗ.
2. **Источник правды по структуре:** порядок и состав элементов цепочек — §4 этого ТЗ. Код дублируется (чистые функции §6.3 → копия в `botRender.ts`), расхождение ловится снапшот-тестом шаблона в ТЗ-10 (заявлено там же, §9).
3. **SPA-мета (title/description):** по ТЗ-10 §6.4 источник правды текстов для ботов — API-шаблон, SPA-мета вторична. Этот ТЗ вносит только `<title>` (should-9); `meta description` и OG в SPA не трогаем.
4. **Пейволл:** для ботов ТЗ-10 отдаёт метаданные + excerpt; разметка BreadcrumbList на 403-экране SPA не выводится (§5) — с серверным шаблоном не конфликтует, т.к. шаблон формирует свою разметку по §4 независимо от ответа API контента.

## 8. Тестирование

Паттерн — как в `scripts/e2e.sh`: curl-smoke в скрипте + ручные проверки в браузере. **Ограничение:** `curl` не исполняет JS, поэтому самого JSON-LD в curl-проверках не будет — curl-блок проверяет только, что dev-сервер отдаёт SPA-корректно и ничего не сломано; наличие разметки проверяется в браузере.

### 8.1 Curl-smoke (добавить блоком в `scripts/e2e.sh` или отдельным `scripts/e2e-web.sh`)

```bash
W="${WEB_URL:-http://localhost:5173}"
# dev-сервер поднят и отдаёт SPA-скелет
curl -s -o /dev/null -w "%{http_code}" "$W/" | grep -q 200
curl -s "$W/" | grep -q '<div id="root">'
curl -s "$W/" | grep -q 'src="/src/main.tsx"'
# SPA-fallback на глубоких путях (сервер не отдаёт 404 на клиентском роуте)
curl -s -o /dev/null -w "%{http_code}" "$W/novost/spacex-lider-po-kolichestvu-sputnikov" | grep -q 200
# index.html не содержит inline JSON-LD (разметка только из бандла — регрессия «захардкодили скрипт в шаблон»)
curl -s "$W/" | grep -q 'application/ld+json' && echo "ПРОБЛЕМА: ld+json в статическом index.html" || ok
```

Ожидаемый результат фиксируется в выводе PASS/FAIL по аналогии с e2e.sh.
