## Задача 1. Ограничение пароля 72 байтами (быстрый фикс, делается сразу)

**Проблема:** bcryptjs обрезает пароли до 72 байт; `passwordSchema` допускает до 100
символов — два разных длинных пароля могут совпасть после обрезки.

**Решение:** `Buffer.byteLength(p, 'utf8') <= 72` в `passwordSchema`
(`apps/api/src/routes/auth.ts`). Русские символы — 2 байта: сообщение об ошибке
обязано объяснять лимит в байтах, не символах.

**Проверка:** регистрация с паролем 40 русских букв (80 байт) → 400 с понятным
сообщением; 36 букв (72 байта) → проходит.

## Задача 2. Миграция zod 3 → 4 (high, GHSA-mrhx-c7xc-m3w5)

**Проблема:** уязвимость высокой степени, исправлена только в zod 4.

**Решение:** поднять `zod` до `^4.6.7` во всех воркспейсах; пройти typecheck —
ломающие места проекта: `z.string().email()` → `z.email()`, изменения в `z.record`,
`z.infer`, сообщения об ошибках, `.default()` на объектах. Ожидаются ошибки типов во
всех роутах — чинить по месту, семантику валидаций не менять.

**Проверка:** `tsc --noEmit` чисто; 15/15 unit-тестов; смоуки `scripts/auth-smoke.mjs`
и сценарий сброса пароля против живой БД; ручной проход: регистрация/логин/forgot →
verify-code → reset, создание статьи в админке (zod-схемы контента).

## Задача 3. Контейнер без root

**Проблема:** в моноконтейнере supervisord, Caddy, API и PG-супер-роль работают под
root; компрометация любого процесса = root в контейнере + полный доступ к БД.

**Решение (инфраструктурно, по шагам):**
1. Отдельная роль БД `newinvest_app` (без SUPERUSER, владение только на схеме
   приложения; `ALTER ... OWNER` для существующих таблиц) — DDL-миграция + env.
2. Пользователь ОС `app` в Dockerfile.all; Caddy/API под ним (Caddy слушает 80/443 —
   либо `cap_net_bind_service`, либо порт >1024 с публикацией; PostgreSQL и так
   стартует под `postgres` через `su`).
3. `DATABASE_URL` в api.sh — на роль `newinvest_app`; супер-роль только для
   initdb/миграций (отдельный env, не виден API-процессу).

**Проверка:** контейнер стартует с нуля и с существующим volume; `ps aux` внутри
показывает не-root для api/caddy; API-процесс не может выполнить `CREATE EXTENSION`
(проверка инъекцией через psql от роли app); регрессионный смоук auth.

## Задача 4. Мелкий хвост (одним пакетом)

4.1. **JWT `iss`/`aud`** — добавить `{issuer: 'invest-api', audience: 'invest-spa'}`
    в signToken и проверку в verifyToken + reset-password. Токены старого образца
    после деплоя инвалидируются → перелогин всех (приемлемо, анонсировать).
4.2. **Инвалидация resetToken** — хранить `password_changed_at` на юзере; в
    reset-password требовать `iat >= password_changed_at`. Миграция `0021`.
4.3. **Аудит-лог действий админов** — таблица `admin_audit_log`
    (id, admin_id, action, target, meta jsonb, ip, created_at) + запись в
    `PATCH /users/:id`, `POST /notifications/send`, `POST /redirects`, DELETE;
    просмотр — супер-админам. Без логирования payload с секретами.
4.4. **Вычистка старых SVG из /uploads** — разовый скрипт: найти svg,
    пережать в png либо удалить (решает владелец контента), обновить `media.mime`.

**Проверка:** typecheck, тесты, смоуки; для 4.1 — старый токен отклонён, новый
принят; для 4.2 — resetToken, выданный до смены пароля, отклонён.
