# Безопасность: концепция, модель угроз, регламент

Документ фиксирует базовые принципы безопасности проекта, описание инцидента
аудита 2026-11-14 (публично известный JWT-секрет + доверие к payload токена)
и регламент, чтобы класс ошибок не повторялся.

## 1. Концепция

### 1.1. Главный принцип: токен — это только удостоверение личности, никогда не источник прав

JWT доказывает лишь то, что предъявитель знает секрет, которым подписан токен, и что
токен выдан конкретному субъекту (`sub`). **Все полномочия — роль, тариф, блокировка —
живут в базе данных и читаются из неё на каждый запрос.** Payload токена — недоверенные
данные клиента, даже если подпись валидна.

Следствия, зафиксированные в коде:

- `apps/api/src/middleware/auth.ts` → `verifyToken`: после проверки подписи роль и тариф
  берутся строго из таблицы `users` (`role`, `tariff_id`, `tariff_expires_at`, `is_blocked`).
  Заблокированный или удалённый пользователь с валидным токеном — отказ.
- Отзыв прав (смена роли, снятие тарифа, блокировка) действует немедленно, без ожидания
  истечения токена. TTL токена — это максимальное время жизни удостоверения, а не срок
  жизни прав.
- Пейволл (`articles.ts` → `accessCondition`, `cabinet.ts`) строится на `req.user.tariffId`,
  который теперь гарантированно из БД: обход пейволла подделанным `tariffId` в токене
  невозможен по построению.

Практическая цена: один PK-SELECT к `users` на запрос с токеном (анонимы без токена —
ноль). Это осознанная плата за немедленный отзыв прав; при росте нагрузки допустим
короткий TTL-кэш (30–60 с), но отзыв прав тогда станет отложенным — решение принимать явно.

### 1.2. Секреты никогда не живут в репозитории

- В репо допустимы только dev-фолбэки, которые **production-код отказывается принимать**
  (fail fast при старте, а не предупреждение в логе).
- Все секреты (`JWT_SECRET`, `POSTGRES_PASSWORD`, `ADMIN_PASSWORD`, ключи API) задаются
  через окружение: `infra/.env` на сервере (compose-интерполяция `${VAR:?}`) или env
  контейнера. Compose-файл обязан падать на `up` при незаданном секрете, а не
  подставлять молчаливый дефолт.
- Образы не запекают секреты: `Dockerfile.all` не содержит `ENV JWT_SECRET=…`,
  `DATABASE_URL` собирается в `api.sh` при старте из `POSTGRES_*`.

### 1.3. Fail fast, а не fail open

Любая неполная конфигурация безопасности (нет секрета, дефолтный пароль админа,
несовместимый keyGenerator лимитера) должна **останавливать запуск** с понятной ошибкой.
Запуск в деградированном виде «чтобы работало» — запрещён: это всегда fail open.

### 1.4. Многослойность

Безопасность не сводится к одному механизму. Слои: проверка подписи (пиннинг алгоритма
HS256 против alg-confusion) → сверка с БД (роль/тариф/блокировка) → `requireRole` на
роутах → проверки на уровне данных (zod-схемы) → rate-limit → security-заголовки.
Просадка одного слоя не должна давать полный доступ.

### 1.5. Аудируемость

Каждое изменение в контур безопасности сопровождается: датой, ссылкой на код,
смоук-тестом (см. `scripts/auth-smoke.mjs`) и записью в раздел 3 этого документа.

## 2. Модель угроз (актуальные поверхности)

| Угроза | Митигация | Где |
|---|---|---|
| Подделка JWT известным/утёкшим секретом | Секрет ≥ 32 символов, вне репо; fail fast в `config.ts`; права из БД не зависят от payload | `config.ts`, `middleware/auth.ts` |
| Обход пейволла подделанным `tariffId` | Тариф только из `users` на каждый запрос | `middleware/auth.ts`, `articles.ts` |
| Доступ заблокированного/уволенного админа по старому токену | `is_blocked` проверяется в `verifyToken` (раньше — только в `requireRole`) | `middleware/auth.ts` |
| Перебор пароля | `loginLimiter` | `middleware/security.ts` |
| Обход rate-limit с IPv6 (ротация адресов) | `ipKeyGenerator` — нормализация IPv6-подсетей | `routes/engagement.ts` |
| Alg-confusion (RS256→None/HS256) | Пиннинг `algorithms: ['HS256']` в `jwt.verify` | `middleware/auth.ts` |
| Дефолтный пароль супер-админа (`admin123`) | Seed отказывается стартовать в production с дефолтом; обход через `NODE_ENV=development` убран | `seed.ts`, `api.sh` |
| Выгрузка персональных данных (email) | Роут за `authRequired + requireRole(ADMIN_ROLES)`; права из БД | `routes/admin.ts` |
| Стенд с дефолтными креденшелами, открытый в LAN/интернет | Секреты обязательны (`${VAR:?}` + fail fast в сиде); порты биндятся на `127.0.0.1` по умолчанию (`BIND_ADDR`), LAN-бинд — осознанное действие с сильными секретами | `docker-compose.all.yml`, `DEPLOY.md` |
| Утечка через заголовки/фингерпринт | `X-Powered-By` отключён, security-заголовки | `index.ts`, `middleware/security.ts` |
| CSRF на мутациях | Bearer-токен (не cookie) + CORS-allowlist | `index.ts`, `middleware/security.ts` |

## 3. Инциденты и исправления

### 2026-11-14 — публично известный JWT-секрет + доверие к payload (критично)

**Найдено (аудит кода):**

1. Дефолтный секрет `local-dev-secret-change-me` стоял в `docker-compose.yml`
   (`${JWT_SECRET:-…}`), был захардкожен в `docker-compose.all.yml` и запечён в
   `Dockerfile.all`. Защита в `index.ts` сравнивала секрет со строкой
   `dev-secret-change-me` — с фактическим дефолтом не совпадала никогда, проверка мертва.
2. `verifyToken` брал `role`, `tariffId`, `tariffExpiresAt` прямо из payload без сверки с БД.
3. `api.sh` запускал сид с `NODE_ENV=development`, обходя guard дефолтного `ADMIN_PASSWORD=admin123`
   — супер-админ реально создавался на стенде с опубликованными креденшелами.
4. Там же захардкожены `POSTGRES_PASSWORD` и `DATABASE_URL` с паролем.
5. Моноконтейнер слушал `80/443` на всех интерфейсах (`0.0.0.0`), а по DEPLOY.md домен
   вёлся на LAN-IP — стенд с дефолтными креденшелами был доступен любому в сети
   (и пробросимым роутером — извне).

**Эксплуатация (до фикса):** подписать токен `{role:"super_admin", tariffId:<N>}` известным
секретом → выгрузка базы email (`/api/users/export.csv`), назначение ролей и тарифов,
публикация контента, запуск дайджестов, чтение всех платных материалов. Для пункта 5
достаточно логина `admin@local / admin123` с любого устройства сети — полный захват
админки без единого эксплойта.

**Исправлено:**

- `config.ts`: в production секрет обязателен, ≥ 32 символов, оба известных дефолта
  отвергаются; throw до старта сервера. Мёртвый guard удалён из `index.ts`.
- `middleware/auth.ts`: `verifyToken` сверяет роль/тариф/блокировку с БД; payload игнорируется.
- `docker-compose.all.yml`: `POSTGRES_PASSWORD`, `ADMIN_PASSWORD`, `JWT_SECRET` — обязательные
  через `${VAR:?}` (падение на `up`). `Dockerfile.all` очищен от секретов; `DATABASE_URL`
  собирается в `api.sh` при старте. `api.sh` — без обхода `NODE_ENV` и без проглатывания
  ошибки сида.
- `docker-compose.local.yml`: локальный стек явно в `NODE_ENV: development` (dev-дефолты допустимы).
- `docker-compose.all.yml`: порты биндятся на `${BIND_ADDR:-127.0.0.1}` — стенд по умолчанию
  недоступен из LAN; LAN-бинд — осознанное решение (переменная в `infra/.env` + сильные
  секреты, проброс портов в интернет запрещён). `ADMIN_EMAIL` переопределяется через env.
- `engagement.ts`: `keyGenerator` анонимного лимитера переведён на `ipKeyGenerator`
  (нормализация IPv6) — закрыт обход rate-limit; заодно починен запуск API под Node 24.
- `DEPLOY.md`, `.env.example` дополнены требованиями к секретам.

**Проверка:** `scripts/auth-smoke.mjs` (смоук против живой БД, 4/4): подделанный
`super_admin` → 403; верно подписанный токен реального админа с `role=reader` в payload → 200
(права из БД); легитимный reader → 403; поддельный `tariffId` не открывает платные материалы.

## 4. Регламент

1. **Новый секрет** — только через env; запрещено: значение в compose/Dockerfile/коде,
   дефолт через `${VAR:-секрет}`. Проверка в коде — по классу значения (длина, не из
   списка известных), а не побайтовое равенство одной строке.
2. **Новый привилегированный роут** — `authRequired + requireRole(...)`; права читаются
   из `req.user`, который гарантированно из БД.
3. **Любое использование данных из JWT** — только `sub`; всё остальное из payload
   считается недоверенным.
4. **Кастомный `keyGenerator` у rate-limit** — только через `ipKeyGenerator` для IP-ключей.
5. **Смена контура безопасности** — обновить раздел 3, прогнать `npm run typecheck`,
   `npm run test -w @newinvest/api` и `scripts/auth-smoke.mjs` (нужен локальный Postgres
   и `JWT_SECRET` той же силы, что в проде).
6. **Ротация секретов**: немедленно при малейшем подозрении на утечку; смена `JWT_SECRET`
   инвалидирует все сессии (перелогин всех пользователей — приемлемо, анонсировать).
7. **Перед выводом стека в LAN/интернет** — чек-лист: `infra/.env` создан, секреты не
   дефолтные, API стартует без ошибок guard'ов, `export.csv` и `/api/users` отвечают 401
   без токена и 403 с токеном reader.
