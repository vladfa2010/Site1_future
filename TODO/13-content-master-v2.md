## Фича 1: Персистентные сессии

### Требования
1. Две таблицы (миграция `0022_content_master_sessions.sql` + drizzle-схема + ручная запись в `meta/_journal.json`, конвенция 0020/0021):
   - `cm_sessions`: id, user_id → users ON DELETE CASCADE, title (производный, до 200 симв.), source (исходник целиком: текст или URL), mode, search, created_at, updated_at;
   - `cm_messages`: id, session_id → cm_sessions ON DELETE CASCADE, role ('user'|'assistant'), instruction (для обоих ролей — нужен для контекста), result_json (только assistant: полный JSON результата), created_at.
   - Индексы: `cm_messages_session_idx(session_id)`, `cm_sessions_user_idx(user_id, updated_at)`.
2. API (всё под authRequired + requireRole('admin','super_admin'), лимитер существующий):
   - `GET /api/admin/content-master/sessions` — сессии ТЕКУЩЕГО юзера, последние 50, с `updatedAt` и числом сообщений.
   - `GET /api/admin/content-master/sessions/:id` — сессия + сообщения целиком (404 если чужая/нет).
   - `DELETE /api/admin/content-master/sessions/:id` — только своя (403 если чужая), каскад удаляет сообщения.
3. `POST /rewrite` принимает опциональный `sessionId`. Если передан — валидация владельца (чужая → 403), история сообщений подмешивается в контекст модели (фича 2), ответ сохраняется в сессию (user + assistant сообщения за один запрос). Если не передан — создаётся новая сессия, ответ содержит `sessionId`.
4. `updated_at` сессии обновляется на каждый запрос в неё. `title` — из первого полученного заголовка рерайта (до первого ответа — первые 80 символов source или hostname ссылки).

### Критерии приёмки
- [ ] Рерайт без sessionId создаёт сессию, ответ содержит её id; повторный запрос с этим id пишет в ту же сессию.
- [ ] Список сессий видит только свои; чужая сессия → 403 (GET/DELETE), несуществующая → 404.
- [ ] Обновление страницы: GET /sessions/:id восстанавливает чат полностью (источник, инструкции, результаты, выбранный «активный»).
- [ ] Удаление сессии удаляет сообщения (проверка по БД).

## Фича 2: Итеративный чат (контекст предыдущих ответов)

### Требования
1. При `sessionId` в `messages` запроса к LLM добавляются предыдущие ходы: для каждого `user` — инструкция (+ исходный текст ТОЛЬКО в первом ходу), для каждого `assistant` — компактное представление результата:
   - rewrite: `Заголовок: …\n\n<html→plain text, обрезка 1500 симв.>`;
   - factcheck: список `утверждение — статус — комментарий` (обрезка 1500 симв.) + summary.
2. Контекст: последние 8 ходов (пара user+assistant), дальше отсекается — бюджет модели не жрём.
3. Источники (sources) прошлых ходов в контекст НЕ подмешиваются (шум), живут в result_json и рендерятся в UI.

### Критерии приёмки
- [ ] В сессии работает «сделай короче» / «добавь контекст» без повторной вставки исходника — модель опирается на предыдущий ответ.
- [ ] Без sessionId поведение прежнее (одиночный рерайт без контекста).

## Фича 3: SSE-стриминг ответа

### Требования
1. `POST /rewrite` с `"stream": true` (или `Accept: text/event-stream`) отвечает `text/event-stream`: заголовки `Cache-Control: no-cache`, `X-Accel-Buffering: no`.
2. События (строки `data: {json}`):
   - `meta` — `{sessionId, mode, mock?, sourceUrl, truncated}` — сразу после старта;
   - `delta` — `{text}` — куски финального контента LLM;
   - `done` — полный разобранный результат (`title/html/excerpt` или `report/summary` + `sources`, `usage`);
   - `error` — `{message}` + закрытие потока.
3. Стримится ТОЛЬКО финальный раунд LLM. Раунды с tool_calls (агентный поиск) и выкачивание URL — не стримятся, клиент это время видит как «думает».
4. Стриминг поддержан для обоих провайдеров (OpenAI-совместимый SSE: `stream: true`, дельты `choices[0].delta.content`, финал `data: [DONE]`). DeepSeek и Kimi/Moonshot оба совместимы.
5. Клиент — `fetch` + `ReadableStream` (EventSource не умеет Authorization-заголовок). Парсинг накопительный по `\n\n`-чанкам.
6. В UI текст появляется по мере генерации; после `done` результат нормализуется в карточку (как сейчас). Mock-режим не стримится (мгновенный ответ, как сейчас).
7. Фактчек тоже стримится (это тот же контент-стрим; парсинг JSON — после сборки).
8. `usage: {promptTokens, completionTokens, totalTokens}` — от провайдера, пробрасывается в `done` (не в стриме). В нестрим-ответе тоже добавить.

### Критерии приёмки
- [ ] Стрим-запрос: meta приходит до первой дельты; дельты склеиваются в валидный результат, `done` парсится без ошибок.
- [ ] Ошибка LLM в середине стрима → событие `error`, соединение закрыто, UI показывает сообщение.
- [ ] Нестрим-режим (`stream` не передан) работает как раньше + новые поля.
- [ ] Аноним/reader на стрим-эндпоинте — 401/403 до старта SSE.

## Фича 4: Мелочи

1. **Обрезка исходника**: source > 15 000 симв. → в ответ/meta добавляется `truncated: true`; UI — жёлтое предупреждение «исходный текст обрезан до 15 000 символов, хвост не передан модели».
2. **Источник в черновик**: если в форме черновика sourceUrl пуст, а у активного результата есть sources — автоподстановка первого URL (ручное редактирование не ломается).
3. **Usage в UI**: под активным результатом мелким шрифтом «N токенов (in X / out Y)».
4. **Тренды — серверная фильтрация**: `GET /api/trends?q=` (ilike по name, limit 20) вместо выкачивания всех 100 и фильтрации на клиенте; TagInput трендов шлёт q. Обратная совместимость: без q — как раньше (100 шт., сортировка по name).

### Критерии приёмки
- [ ] source 20 000 симв. → truncated:true и предупреждение в UI.
- [ ] Результат с sources, пустой sourceUrl → форма черновика подставляет первый URL.
- [ ] `/api/trends?q=космос` → только совпадения; без q — прежнее поведение.

## E2E (scripts/e2e.sh)
- sessions: anon 401, reader 403; создание через rewrite (sessionId в ответе); GET список содержит сессию; GET :id содержит 2 сообщения; чужая сессия 403; DELETE своя 200 + повторный GET 404.
- итеративность: второй rewrite с sessionId и инструкцией «сделай короче» → ответ отличается и опирается на первый (проверяем минимум: 200 + title/html на месте).
- стриминг: POST с stream:true, Accept text/event-stream → заголовок Content-Type text/event-stream, тело содержит `data: {` с meta и `done` (проверка grep'ом); нестрим-ответ содержит usage.
- truncated: source 20 000 симв. → `"truncated":true`.
- trends: `?q=` фильтрует (e2e-данные: есть тренд «космос»), без q — 100.
- регрессии прежних cm-тестов (anon 401, reader 403, рерайт, SSRF 400, валидация) не сломаны.
