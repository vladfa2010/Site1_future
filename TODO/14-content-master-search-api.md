# ТЗ-14: ContentMaster — надёжный поиск в интернете (Tavily/Brave)

Статус: 📝 ТЗ (не реализовано, принято к планированию 2026-11-15)
Дата: 2026-11-15
Контекст: агентный поиск ContentMaster (`chatWithSearch` в `apps/api/src/routes/contentMaster.ts`).
Исполнение поиска для Kimi — скрейпинг DuckDuckGo lite без ключа. Хрупко: антибот отдаёт
202-челлендж при бёрстах и режет по IP (зафиксировано в `docs/newinvesticionno.md`, строка 900:
«в проде (единицы запросов в день) ок, при объёмах нужен Tavily/Brave API»).

---

## Проблема
1. DDG lite — непубличный, нестабильный интерфейс: любое изменение разметки или усиление
   антибота ломает поиск для всего провайдера Kimi.
2. Ретраи с бэкоффом 2.5/5 с + паузы 350 мс между запросами делают агентный цикл медленным
   и всё равно не гарантируют результат.
3. Выдача без ранжирования по авторитетности/скору — первые 5 сниппетов, не лучшие 5.
4. Нет кэша: повторные/похожие запросы модели бьют в поисковик заново.

## Цель
Поисковый исполнитель с официальным API, ранжированием, кэшем и честной деградацией.

## Варианты провайдера

| Провайдер | Бесплатный лимит | Плюсы | Минусы |
|---|---|---|---|
| Tavily | 1000 запросов/мес | Ранжирование «search depth», extract-эндпоинт (готовый текст страницы), JSON без скрейпинга | Требует ключ, лимит жёсткий на бесплатном плане |
| Brave Search API | 2000 запросов/мес, 1 qps | Высокое качество ранжирования, отдельные поля extra_snippets | Требует ключ, 1 qps — нужен клиентский троттлинг |
| DDG (текущий) | ∞ | Без ключа | Хрупкий, антибот, без ранжирования — оставить ТОЛЬКО как последний fallback |

## Требования
1. **Настройки**: ключ(и) поискового API — в `kimiSettings` (та же модель хранения meta_fields,
   что и LLM-ключи): `search_provider` ('tavily'|'brave'|'none'), `tavily_api_key`,
   `brave_api_key`. UI — `KimiSettingsPage` (маскированный ввод, как у LLM-ключей).
2. **Исполнитель**: абстракция `SearchExecutor` (уже есть — `executeSearch` в `chatWithSearch`),
   добавить реализации `tavilySearch`, `braveSearch`. Порядок выбора: нативный Search API
   DeepSeek (если провайдер deepseek) → настроенный Tavily/Brave → DDG как fallback →
   честная деградация «поиск недоступен» (текущее поведение).
3. **Кэш**: таблица `cm_search_cache` (query_hash, query, provider, results_json, created_at,
   TTL 24 ч; hit → без запроса к провайдеру). Индекс по query_hash (sha256).
4. **Троттлинг**: Brave — 1 qps: минимальный интервал между запросами 1.1 с на уровне
   исполнителя (не ломать параллельные сессии — очередь/лок в процессе достаточно).
5. **Лимиты**: query до 400 симв. (Tavily/Brave вмещают), count 5, таймаут 15 с,
   ретраи — максимум 1 (API стабильнее DDG, агрессивный бэкофф не нужен).
6. **Расход**: в ответ ContentMaster добавить `searchUsed: {provider, cached: boolean}`
   рядом с usage — видно в UI, сколько уходит на поиск.
7. **Безопасность**: ключи только сервер-сайд; в UI — маскированные; в логи не писать.

## Что НЕ входит
- Смена модели/промптов фактчека и рерайта (ТЗ-13 покрывает UX).
- Поисковый кэш между юзерами (кэш глобальный по query_hash — этого достаточно, текст запроса
  не персональный).

## Критерии приёмки
- [ ] С ключом Tavily/Brave поиск для Kimi идёт через API, выдача содержит url+title+snippet.
- [ ] Повторный тот же запрос в пределах 24 ч → `cached: true`, внешний запрос не выполняется.
- [ ] Без ключа поведение = текущее (DDG → честная деградация).
- [ ] Ключи маскируются в настройках, полные не утекают в API-ответы и логи.
- [ ] E2E: с mock-ключом Tavily — формируется правильный URL/заголовки (проверка конфигурации,
  без реального вызова).

## E2E (scripts/e2e.sh)
- kimi-settings принимает/маскирует tavily_api_key, валидирует search_provider.
- cm_search_cache: после двух одинаковых поисковых запросов в рамках одной сессии — 1 запись.

## Зависимости
ТЗ-13 (сессии) — желательно сделано раньше: кэш и searchUsed опираются на его инфраструктуру,
но блокирующей зависимости нет (таблицы не пересекаются).

## Реализация (план)

- `apps/api/src/routes/kimiSettings.ts`: приём/маскирование новых ключей.

- `scripts/e2e.sh`: проверки настроек и кэша.
